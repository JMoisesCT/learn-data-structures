Merge sort and quicksort

Two divide and conquer algorithms: they split the array, sort each part with a recursive call and combine. That's how they go down from O(n²) to O(n log n), and why they sort a million values in an instant.

The key piece: merging two sorted halves

Divide and conquer: split, solve each part with the same function and combine. Merge sort does its work when combining, with merge.

With the halves sorted, the smallest is one of the two fronts (v[i] or v[j]): it goes down to aux and that side moves forward. One pass: O(n).

partition: the smaller ones on one side, the larger ones on the other

Quicksort does its work when dividing. With a pivot (here, the last one), j walks the range and each value ≤ pivot moves with a swap to the end of the zone of the smaller ones, which ends at i. Then the pivot goes right after it: it ends up in its final place.

quickSort: partition and sort each side

After partition, the pivot stays put: two recursive calls sort each side, and there's nothing to combine on the way back.

Quicksort's worst case, and how to avoid it

If the pivot is always the largest (or the smallest), each partition splits off a single element: n levels and O(n²). With the last one as the pivot, that happens precisely with an already sorted array; with a random pivot, no array is always the worst.

What's dangerous about the staircase with n = 1,000,000 in C++?

quickselect: the k-th smallest without sorting everything

To know which value would end up in v[k] (like the median) you don't need to sort. After partition, if p == k it's done; if not, it goes on only with k's side and the other one is discarded. On average, n + n/2 + n/4 + … = O(n).

Why is quickselect O(n) on average and quicksort O(n log n)?

heapSort (Heap)O(n log n)O(n log n)O(n log n)O(1)No
quickselectO(n)O(n)O(n²)O(log n) of stack—
  • Lower bound: no sort that only compares can make fewer than about log₂(n!) ≈ n log n comparisons in the worst case. Merge sort and heapsort are already at that bound.
  • Quicksort is usually the fastest in practice: it walks memory in order and doesn't copy to another array.
  • std::sort is introsort: a quicksort that switches to heapsort if the recursion gets too deep and to insertion sort for the small pieces. O(n log n) guaranteed.
  • std::stable_sort is merge sort: use it when equal values must keep their order. Python and Java use Timsort, a merge sort that takes advantage of runs that are already sorted.
  • Merge sort also works for linked lists (they're merged by moving pointers, without aux) and for sorting files that don't fit in memory.
  • std::nth_element does what quickselect does. To beat n log n you have to not compare: you'll see it in the next topic.

Practice

  1. Change merge's <= to <. Does it still sort? Is it still stable?
  2. Make merge reserve aux only once (with aux.reserve or a vector passed by reference) and measure the difference.
  3. Write Hoare's partition: two indices that move in from the ends and swap when both find a value on the wrong side.
  4. Make quickSort call insertionSort when the range has fewer than 16 elements (that's what std::sort does).
  5. To avoid overflowing the stack: make the recursive call only with the smaller side and repeat with the larger one in a while. How much stack does it use in the worst case?
