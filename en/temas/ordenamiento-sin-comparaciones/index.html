Non-comparison sorting

Sorting by comparing pairs never goes below O(n log n). These algorithms don't compare: they use the value itself as the index of an array or of a bucket. With small keys they reach O(n).

Count instead of compare

If the values are integers between 0 and maxValue, there's no need to compare them: each value x adds 1 to count[x], using the value as an index.

Then v is rewritten going through the values in order: as many 0s as count[0] says, as many 1s as count[1] says… Total: O(n + k), with k = maxValue + 1.

countingSort: running sums and stability

After counting, the running sums turn count[x] into "how many values are ≤ x": where the last x ends in the output. Walking v from right to left, each value (with its whole record) goes to output[--count[x]]: equal values keep their order.

Why does the last for walk v from right to left?

radixSort: one counting sort per digit

With large numbers (up to 802), count would need 803 slots. Radix sort uses only 10: it sorts by the ones, then by the tens, then by the hundreds. Each pass is stable, so it doesn't undo what the earlier ones sorted.

Why does it start with the ones and not with the hundreds?

bucketSort: distributing into buckets

Each value goes to the bucket of its range (0 to 19, 20 to 39…) without being compared with anything. Then each bucket, which has few values, is sorted, and they are emptied in order. If the values are spread evenly, it's O(n) on average; if they cluster, all the work falls on one bucket.

Complexity and when to use each one

AlgorithmTimeExtra memoryStableGood for
countAndRewriteO(n + k)O(k)—Bare integers in a small range
countingSortO(n + k)O(n + k)YesRecords with a small integer key (grades, ages, days)
radixSort (LSD)O(d · (n + b))O(n + b)YesLarge integers, strings of equal length (b = 10 digits, or 256 per byte)
bucketSortO(n) average, O(n²) worstO(n + buckets)If the sort inside isValues spread evenly over an interval
  • They beat O(n log n) because they don't compare: the n log n limit only holds for the ones that decide by comparing pairs.
  • The price is memory (count, output, buckets) and that the keys have to work as an index.
  • With k much larger than n, counting sort is worse than std::sort: radix sort splits the key into digits to avoid it.
  • Radix sort by bytes (base 256) is used to sort millions of integers or IP addresses; databases and GPUs use it a lot.
  • Stable counting sort is the building block of radix sort, and the way to sort records by a small key while keeping their previous order.
  • The STL has no counting or radix sort: they're written by hand when std::sort isn't enough.

Practice

  1. Make countingSort accept negatives: find the minimum and use count[x - minValue].
  2. Write a countingSort that sorts struct Student { string name; int grade; } by grade and check that it's stable.
  3. Change the base of radixSort from 10 to 256 (using (x >> (8 * pass)) & 255). How many passes are needed for a 32-bit int?
  4. Try bucketSort with numBuckets = n and random values: how many values does each bucket have, on average?
