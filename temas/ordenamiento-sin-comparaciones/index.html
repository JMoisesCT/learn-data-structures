Ordenamientos sin comparaciones

Ordenar comparando pares nunca baja de O(n log n). Estos algoritmos no comparan: usan el valor mismo como índice de un arreglo o de una cubeta. Con claves chicas llegan a O(n).

Contar en vez de comparar

Si los valores son enteros entre 0 y maximo, no hace falta compararlos: cada valor x suma 1 en conteo[x], usando el valor como índice.

Después se reescribe v recorriendo los valores en orden: tantos 0 como diga conteo[0], tantos 1 como diga conteo[1]… Total: O(n + k), con k = maximo + 1.

¿Qué problema tiene contarYReescribir si cada valor es la nota de un alumno y queremos ordenar alumnos?

countingSort: sumas acumuladas y estabilidad

Después de contar, las sumas acumuladas convierten conteo[x] en "cuántos valores son ≤ x": dónde termina el último x en la salida. Recorriendo v de derecha a izquierda, cada valor (con todo su registro) va a salida[--conteo[x]]: los iguales conservan su orden.

¿Por qué el último for recorre v de derecha a izquierda?

radixSort: un counting sort por cada dígito

Con números grandes (hasta 802), conteo necesitaría 803 casillas. Radix sort usa solo 10: ordena por las unidades, después por las decenas, después por las centenas. Cada pasada es estable, así que no deshace lo que ordenaron las anteriores.

¿Por qué empieza por las unidades y no por las centenas?

bucketSort: repartir en cubetas

Cada valor va a la cubeta de su tramo (de 0 a 19, de 20 a 39…) sin compararse con nadie. Después se ordena cada cubeta, que tiene pocos valores, y se vacían en orden. Si los valores están repartidos parejo, es O(n) en promedio; si se amontonan, todo el trabajo cae en una cubeta.

Pruébalos todos

Elige un algoritmo y ordena; Reiniciar trae otro arreglo al azar. Mira el contador: nunca hay una comparación entre dos valores.

  • Ganan a O(n log n) porque no comparan: el límite de n log n solo vale para los que deciden comparando pares.
  • El precio es la memoria (conteo, salida, cubetas) y que las claves tienen que servir de índice.
  • Con k mucho mayor que n, counting sort es peor que std::sort: radix sort parte la clave en dígitos para evitarlo.
  • Radix sort por bytes (base 256) se usa para ordenar millones de enteros o direcciones IP; las bases de datos y las GPU lo usan mucho.
  • Counting sort estable es la pieza de radix sort, y la forma de ordenar registros por una clave chica conservando el orden anterior.
  • En la STL no hay counting ni radix sort: se escriben a mano cuando std::sort no alcanza.

Código completo en C++

Compílalo y ejecútalo con:

g++ -std=c++17 -Wall -Wextra ordenamiento_sin_comparaciones.cpp -o ordenamiento_sin_comparaciones && ./ordenamiento_sin_comparaciones

Para practicar

  1. Haz que countingSort acepte negativos: busca el mínimo y usa conteo[x - minimo].
  2. Escribe un countingSort que ordene struct Alumno { string nombre; int nota; } por nota y comprueba que es estable.
  3. Cambia la base de radixSort de 10 a 256 (usando (x >> (8 * pasada)) & 255). ¿Cuántas pasadas hacen falta para un int de 32 bits?
  4. Prueba bucketSort con cubetas = n y valores al azar: ¿cuántos valores tiene, en promedio, cada cubeta?
  5. ¿Qué pasa si recorres el último for de countingSort de izquierda a derecha? Ordena, pero ¿qué pasa con 4ᵃ y 4ᵇ?
