Linked list

Nodes scattered around memory, each with a value and a pointer to the next one: the idea behind std::forward_list.

Nodes that point to each other

struct Node {    int value;    Node* next;  // nullptr if it's the last one};

Like a treasure hunt: each node says where the next one is. They are created with new wherever there is room and the list only keeps head: reaching pos costs pos jumps. That's what nodeAt(pos) does, and get, insertAt and removeAt use it: O(n).

How many times does current = current->next run in nodeAt(3)?

insertAtFront: two pointers and done

The node is created, made to point to the current first one, and head moves to it. It doesn't matter whether the list has 3 nodes or a million: it's always the same steps, O(1). (In an array, inserting at the front shifts every element.)

What happens if you swap the order and do head = newNode before newNode->next = head?

insertAt(pos, value): reach the previous node and hook in

For the new node to end up at position pos, the previous node (the one at pos - 1) has to point to it. nodeAt(pos - 1) takes us to that node; after that, hooking in is just two pointers. If pos is 0 there is no previous node, and insertAtFront is reused.

Why ask for nodeAt(pos - 1) and not nodeAt(pos)?

With 4 nodes (positions 0 to 3), is insertAt(4, x) valid?

insertAtBack: one line, but O(n)

The end is position size, so insertAtBack just calls insertAt(size, value), which calls nodeAt(size - 1). The code is short, but nodeAt still walks the list to the last node: it's still O(n). Watch the call stack above the drawing.

How could you make insertAtBack O(1)?

find(value): node by node

current moves forward from the head comparing each value. If it reaches nullptr, the list is over and the value isn't there. In the worst case it checks every node: O(n).

If the list were sorted, would binary search work like in an array?

remove(value): unhook and free

To take a node out, the previous node has to point to the one after the deleted node. Since pointers go in only one direction, current stops one node early and looks at current->next. Then delete frees the memory. Deleting the head is a separate case: it has no previous node, so head moves.

removeAt(pos): delete by position

It's the same idea as insertAt: nodeAt(pos - 1) takes us to the previous node, which now points past the deleted one. Before the delete, the value is saved to return it. Here the valid positions go from 0 to size - 1.

List or array?

Neither is better at everything. Pick an operation and change the number of elements: each bar is the work each structure does (green: the one that does less).

The list shines when you insert or delete at the front or next to a node you already have at hand. For anything that needs to reach a position, the array wins, and almost always when traversing too, thanks to the cache.

  • Use it when you insert and remove a lot at the front, or next to nodes you have already located (for example, with a saved iterator).
  • It's the basis of other structures: stacks, queues, graph adjacency lists and the buckets of a hash table with chaining.
  • A not-so-obvious advantage: inserting or deleting nodes doesn't move the others, so pointers to other nodes stay valid (in an array, after a resize, they don't).
  • Avoid it if you access by position or traverse a lot: std::vector is usually faster thanks to the cache, and uses less memory per element. Measure before choosing.
  • std::list is the doubly linked version: each node also points to the previous one, so it can be traversed in both directions and a node can be deleted without looking for its previous node.

Practice

  1. Add a tail pointer to the last node so that insertAtBack is O(1) without calling nodeAt. Which other methods do you have to update?
  2. Write void set(int pos, int value) using nodeAt. What do you do if it returns nullptr?
  3. Write void reverse() that turns the list around by changing only pointers, without creating nodes. (Hint: you need three pointers: previous, current and next.)
